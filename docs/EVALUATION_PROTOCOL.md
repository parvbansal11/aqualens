# EVALUATION PROTOCOL

**Rule zero: the word "accuracy" appears in no headline result.** On a task with this class
imbalance it is meaningless — a model detecting nothing scores above 99 %.

**Rule one: no metric appears in the frontend or any report unless it was reproducibly
generated by a pipeline run and published through `benchmarks.json`.**

---

## 1. Splits

Group-wise, assigned **at frame level before tiling**. Tiles at 50 % overlap are
near-duplicates by construction; a tile-level split leaks by definition and
`sagar.evaluation` refuses one.

| Dataset | `group_key` | Strength |
|---|---|---|
| SubPipe | mission / chunk id | STRONG |
| AI4Shipwrecks | wreck / site id — **use the official split as given** | STRONG |
| PINGEcosystem | recording id; fallback filename/spatial block | **WEAK — must be disclosed in any result using it** |

| Split | Purpose | Rule |
|---|---|---|
| train | fit the detector, build the open-set memory bank | — |
| val | thresholds, isotonic calibration, fusion coefficients, early stopping | never reported |
| test | every reported number | touched once per release, never for tuning |

Approximately 70/15/15 **by group**, not by image count.

Held-out **domains** as well as groups: at least one frequency band (SubPipe LF vs HF) is
reserved so cross-frequency robustness is measured rather than assumed. SubPipe (Atlantic
coastal, Klein 3500) and AI4Shipwrecks (Great Lakes freshwater, different sensor) form a natural
cross-domain pair — report per-dataset results separately and never average them into a single
headline without saying so.

---

## 2. Leakage safeguards

Six assertions. Five run inside every pipeline run and land in `RunManifest.split_assertions`;
the sixth guards the feedback loop.

```
A. group overlap train ∩ test         == ∅
B. group overlap train ∩ val          == ∅
C. perceptual-hash near-duplicates across splits (Hamming ≤ τ)  == 0
D. rows with eval_eligible == false in val/test                 == 0
E. every test group contains ≥ 1 positive
F. every training-eligible reviewed detection comes from a frame NOT in the active val/test split
```

`scripts/make_benchmarks.py` **refuses to publish** metrics from a run where any of A–E failed.
`tests/test_feedback_leakage.py` asserts F.

F is the one that is easy to lose. The memory layer feeds operator-reviewed detections back into
training; if a reviewed detection came from a test frame, the test set is silently destroyed and
every subsequent number is worthless. It is guarded in code, not by discipline.

## 3. Metrics

### Detection (primary)
Precision · Recall · F1 · mAP@0.5 · mAP@0.5:0.95

Reported **overall and broken out per class, per dataset, per site, per frequency**. Single
aggregates hide domain collapse — the GhostNetZero Baltic→Puget lesson is that the aggregate
looks fine while one domain is broken.

Where PINGEcosystem is present, reported under both a **strict** protocol (`CERTAIN` labels
only) and an **inclusive** protocol (`Maybe-Crab-Pot` counted).

### Segmentation (P1, if implemented)
IoU · Dice, per site, on the site-held-out split.

### Open-set / unknown anomaly (KING USP)
**Leave-one-class-out.** Train the detector on all classes but one; treat the held-out class as
genuinely unknown; measure whether the open-set path flags it.

```
Report per fold and mean:
  region-level AUROC
  region-level AUPRC          ← weight this above AUROC; positives are rare
  FPR on annotation-free seabed regions
```

2 folds with the P0 class set, 3 if PINGEcosystem is unblocked.

### Operational
- **False positives per km of trackline** and per 1,000 pings — the number an operator actually
  cares about. F1 never tells them how many boxes they must review.
- Latency p50 / p95 per pipeline stage · FPS · model size on disk · peak RSS
- **Full-survey processing ratio** (survey duration ÷ end-to-end processing time), measured on a
  complete recording rather than per tile. GhostVision reported ~10–11× ✅; that is the
  operating regime, cited as context and **not as a target we claim to beat**.

### Calibration (feasible, therefore required)
Expected Calibration Error and a reliability diagram, before and after isotonic calibration, on
the val split. This is cheap and it substantiates the claim that a confidence number means
something.

## 4. Baseline comparison

| | Model | Device | Classes |
|---|---|---|---|
| Baseline | `PINGEcosystem/gv-yolo12` (ONNX, off-the-shelf) | `onnxruntime:CPUExecutionProvider` | Crab-Pot only |
| Ours | fine-tuned YOLO-s | `mps` | 2–3 unified |

**Mandatory qualification, printed adjacent to the comparison everywhere it appears:** the
baseline is a single-class crab-pot model evaluated on a test split containing pipelines and
wrecks. This measures **transfer of an off-the-shelf sonar model to unseen target types** — it
is *not* a like-for-like contest and "we beat GhostVision" is a forbidden claim
(`docs/CLAIMS_AND_EVIDENCE.md`). A fair head-to-head exists only on
`DERELICT_FISHING_GEAR`, and only if PINGEcosystem is unblocked.

Latency is likewise not comparable across rows without stating that the baseline ran on CPU
(ORT has no MPS provider) and ours on MPS. `RunManifest.device` records what actually executed.

## 5. Ablations (internal-appropriate)

Same detector, same test split, evidence progressively enabled. Because `sagar.evidence` holds
no learned weights, these rows differ *only* in evidence — the only version of this comparison
that means anything.

| # | Configuration | Question |
|---|---|---|
| A0 | Detector only, raw confidence | baseline |
| A1 | + isotonic calibration | is the confidence honest? |
| A2 | + temporal persistence | is transient clutter suppressed? |
| A3 | + acoustic shadow | are texture artefacts suppressed? |
| A4 | + context / clutter density | does rock-field suppression work? |
| A5 | Full fused (fitted LR) | does fusion beat any single channel? |
| A6 | Open-set only | unknown detection standalone |

Every row reports P / R / F1 / mAP **and FP-per-km**. An ablation that raises F1 while raising
operator review burden is shown as exactly that, not hidden.

**If fusion does not beat A0, that is the result.** It is reported plainly and the honest
explanation given. Deleting a disappointing ablation row is fabrication.

## 6. Negative-data testing

A detector is only as good as its behaviour where there is nothing to find.

- **Annotation-free seabed set** held out from train: report raw false-positive count and
  FP-per-km. This is the primary rock/clutter false-positive measurement and it directly answers
  official requirement 9.
- **Open-set FPR on natural seabed** — the same set, scored by the anomaly path. A subsystem
  that flags 20 % of ordinary seabed as anomalous is useless regardless of its AUROC.
- **Empty-frame sanity**: frames with no annotation must produce zero known detections at the
  operating threshold; any that do are logged as failure cases, not suppressed.

## 7. Failure-case logging — mandatory, not optional

Every evaluation run writes `runs/<run_id>/artifacts/failure_cases/`:

```
false_positives/   top-50 by confidence, with tile crop + evidence bundle
false_negatives/   top-50 missed ground truths, with tile crop
low_confidence_tp/ true positives that nearly fell below threshold
open_set_fp/       anomaly proposals on annotation-free seabed
```

These are surfaced in the Model Lab UI. **Showing failure cases in the demo is a feature, not an
admission** — it is the fastest way to demonstrate that the evaluation is real, and hiding them
is explicitly forbidden by the project's honesty constraints.

## 8. Hardware and reproducibility statement

Every `metrics.json` records: machine (MacBook Pro M5 Pro, 24 GB unified), OS version, Python
and PyTorch versions, **the device that actually executed** (`mps` / `cpu` /
`onnxruntime:CPUExecutionProvider`), git SHA, config hash, snapshot id, split id, and seed.

MPS has no deterministic mode. We record the seed and state that runs are **reproducible in
configuration, not bit-exact**. Claiming bit-exact reproducibility on MPS would be false.

---

## 9. Provenance chain for every displayed number

```
pipeline run  →  runs/<run_id>/metrics.json
                       │
      scripts/make_benchmarks.py   ← refuses runs with a failed split assertion
                       │
     apps/workstation/public/benchmarks.json  { run_id, git_sha, generated_at, metrics }
                       │
                  UI reads at runtime
```

Enforced by `tests/test_no_hardcoded_metrics.py`: scans `apps/workstation/**` for numeric
literals adjacent to metric identifiers (`map`, `f1`, `precision`, `recall`, `auroc`, `auprc`,
`iou`, `fps`, `latency`, `%`) and fails the build; and asserts every metric key the UI renders
exists in `benchmarks.json`.

The Model Lab displays `run_id` and `git_sha` beside the metrics table. If a judge asks where a
number came from, the answer is already on screen.
